# 从业务进入代码：建议按这个顺序重新掌握

## 先讲一次业务，再看实现

> 操作员需要更新当天库存。第一次导出为空，系统拒绝覆盖，留下失败记录。人工查明原因后重新获取正常导出，看到变更再确认；新任务记录来源，旧失败保留。观察员查询时能同时看到库存日期与最后成功，不能用“最近请求成功”代替真实业务结果。

如果这段话还说不顺，先照着README跑一次空导出与重试，不急着背JWT或事务术语。

## 应能独立解释的五个决定

1. **数据日期先于自然语言解释。** 模型不能把旧快照说成当前库存；就绪必须由明确字段判断。
2. **预检不是执行许可的全部。** 用户授权要绑定内容；源数据、快照版本和有效期都可能变化。
3. **幂等针对重复请求，人工重跑是新的业务动作。** 同一预检不能再执行；新的重试需要来源、原因和再次确认。
4. **执行失败与业务数据失效不同。** 失败不会抹去上次成功的快照；两种事实分别展示。
5. **模型理解问题，业务后端决定能否执行。** 聊天中的“确认”不能变成权限；固定命令不必使用模型。

## 面试容易追问的范围

- 这是单实例锁与数据库唯一键，不是分布式锁或分布式事务。
- H2本地事务能回滚，不代表外部协作平台支持原子回滚。
- 签名预检和JWT不能防止一切越权；这里是明确的本机合成演示身份体系。
- 50%阈值和3个初始参考是演示设计；没有生产误伤率证明。
- 固定规则查询真实读取工具，但不能称为模型正确率或自然语言理解效果。
- 本次没有真实模型质量验收；代码支持可选真实模型，不能将支持接入等同于效果已验证。

## 重新掌握的四次练习

第一次：不看技术描述，用操作员视角跑正常与空导出。

第二次：画出一条请求到数据库的路径，标出预检、授权、创建任务、写事务和失败记录。

第三次：故意重复确认、选择旧预检、切换viewer，说明在哪里被拒绝。

第四次：停止Python，解释为什么Java查询仍可用；再说明进程重启后任务和库存为何保留。

每次只需要讲清“问题→事实→规则→决定人→结果→失败处理”。不要先背整份实现。
